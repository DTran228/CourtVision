# M3 local prototype: video to timestamped shot estimates

Status (September 29, 2026): the local pipeline is implemented and recognizes
both reviewed development attempts. Broader milestone validation is still pending.
The original roadmap calls for a practice clip with about ten shots and a larger
manually labeled evaluation set. Two reused development examples do not replace it.
The user chose to use the three existing clips for now.

## Run the whole workflow

From the project root, using the saved M2 predictions:

```powershell
.\.venv\Scripts\python.exe cv/src/run_pipeline.py cv/sample_videos/threemade.mp4 --reuse-detections cv/output/threemade --recover-ball --output-dir cv/output/my-m3-run
```

Use a new output folder. For a new video, omit `--reuse-detections` to run YOLO
first. Omit `--recover-ball` to keep the model-only detection path. Recovery is
opt-in because it uses color and motion assumptions tuned on these two clips.
Nothing uploads footage or connects to the mobile app/backend.

The output folder contains tracking video/logs under `tracking/`, detailed
candidate evidence and a readable review table under `shots/`, and `session.json`
at the top level. With recovery enabled, `recovered-detections/` preserves the
combined observations separately from the original YOLO results.

`session.json` reports attempt candidates, makes, misses, unknowns, and timestamps.
Every result is provisional. FG% is null when there are no candidates or any
unknown outcomes. Missing attempts can still bias a non-null FG%. A timestamp is
the first observed crossing frame divided by FPS, or candidate start time when no
crossing was observed; it is not the exact release time.

## What changed and why

The old detector missed the ball near the hoop. A lower E-BARD cutoff and a
YOLO11s comparison did not produce a usable observed path in the sampled rim
frames. The second model is not part of the pipeline and requires no new runtime
dependency. Its downloaded weights stay local and ignored by Git.

The optional recovery uses OpenCV and NumPy already present in the environment:

1. Align a 384x384 patch to the detected hoop, with hoop width normalized to 64
   pixels. This reduces the background movement caused by small camera shifts.
2. Compare the patch with the median of up to nine previous patches (five are
   required to start). The median represents the short-term background.
3. Keep changing red/orange pixels, including both ends of OpenCV's hue range.
   Remove small speckles, join nearby pixels, and form candidate boxes using
   size, shape, and position limits relative to the hoop.
4. Require three consecutive descending proposals near the rim before starting
   a recovered path. Follow nearby proposals using recent velocity, rejecting
   stationary fragments, sudden sideways jumps, and upward jumps before contact.
5. Keep the path for at most 0.25 seconds without a match. Never emit an estimated
   position as if it were observed. Reset the background/path when the hoop is
   missing or its position/scale jumps.

Read `src/recovery.py` for the explicit thresholds. They are heuristics tuned on
these clips, not learned parameters or universal basketball rules. Red clothing,
rim fragments, a different ball color, lighting, frame rate, or camera motion can
break them. Some recovered near-net boxes can include rim/net fragments; correct
final outcomes do not prove every intermediate box is correct.

Recovered observations take precedence over model ball boxes on matched frames.
They carry `source: color_motion` and `confidence: null`; we do not invent a model
probability. Other frames retain the original model detections. The tracker and
renderer accept the missing score and display the source as motion.

## Gap and rebound rules

The shot command now allows a bounded missing interval, default 0.25 seconds.
It retains the last observed point but adds no coordinates for missing frames.
After observations resume, it checks track identity and hoop stability. A proxy
crossing can be inferred between observed endpoints across that short interval;
`crossing_gap_frames` records its size. This is weaker evidence than a continuously
observed crossing. `--gap-seconds 0` restores strict analysis with no missing frames.
The `ShotAnalyzer` class retains strict mode by default for explicit callers/tests.

A possible miss can now result from two or more upward observations after a
crossing near the rim, with a cumulative rise of at least 0.3 hoop widths. This
handles a rebound instead of requiring the ball to descend outside the hoop.
Unknown remains the result when evidence expires or changes discontinuously.
The rim is still approximated by the hoop box's top edge; results remain estimates.

| Clip | Output | Event time | Comparison |
| --- | --- | --- | --- |
| threemade | 1 make | 3.9346 s | Matches the provisional visual label. |
| threemiss | 1 miss | 4.5679 s | Matches the provisional visual label. |
| 20secplay | 0 candidates | none | No shot-level ground truth; do not infer that no shots occurred. |

The baseline matched 0/2 reviewed attempts. Recovery plus gap/rebound handling
matches 2/2, with both outcomes agreeing. These are DEVELOPMENT examples used to
tune the rules, not held-out accuracy measurements. There are no extra candidates
in the labeled windows; times outside those windows are not labeled negatives.

`cv/output/m3-20secplay`. Evaluation reports are under each short run's
`evaluation/`. Original labels remain in `experiments/shot-review.json`.
